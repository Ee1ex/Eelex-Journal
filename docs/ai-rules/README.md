# Eelex Code Hub 工程协作规则

本文档承载 `AGENTS.md` 指向的详细工程规则。产品范围读取 `../PRD.md`，文档治理和自动收尾读取 `../README.md`。

## 任务开始

1. 确认当前 Phase 和最新 PROG。
2. 确认当前已批准 REQ、目标、非目标和验收标准。
3. 按需读取关联 BIZ 和 DEV。
4. 找到受影响文件、入口、数据流和测试。
5. 说明当前逻辑、最小改动、风险和验证方式。
6. 用户批准方案后才进入实施。

文档已有答案时不重复询问。存在会改变范围、架构、公开体验、外部服务或成本的未知项时先确认。

## 需求与方案门禁

- 功能实现前必须有已批准 REQ。
- 复杂模块、架构变化或阶段工作必须有已批准 DEV。
- 产品范围或业务规则变化必须有 BIZ，并同步 PRD。
- 范围外想法记录为后续 REQ，不在当前任务实现。
- 当前 REQ 的验收标准必须具体、可检查。

## 实施原则

- 一次只交付一个最小闭环，或 1～2 个紧密相关需求。
- 修改前先读取相关代码、配置和测试，沿用已确认模式。
- 只修改当前任务涉及的文件，不顺手重构无关内容。
- 不覆盖、删除或回滚用户已有修改。
- 不为尚未批准的未来需求提前增加抽象、依赖或基础设施。

博客任务的默认闭环：

```text
文档定位
→ 内容结构或页面需求
→ UI 与交互
→ 响应式与可访问性
→ 测试与验证
→ 文档与进度同步
```

## TypeScript 与数据边界

- 前端、内容处理、测试和脚本默认使用 TypeScript。
- 不使用 `any`、无依据的类型断言、`@ts-ignore` 或关闭规则来掩盖问题。
- 首页、内容列表、内容详情和 SEO 必须消费同一内容模型。
- 必要 MDX 元数据必须在构建或测试阶段校验。
- v1 不引入数据库、自建后端、登录或 CMS。
- 如果未来引入 backend，request/response schema 和推导类型必须放在共享 contract 层，前端不得手写响应类型。

## 前端与公开体验

- 页面必须同时考虑 PC 与手机。
- 导航、筛选、链接和实验交互必须支持键盘操作。
- 动效用于反馈状态或帮助理解变化，不干扰阅读。
- 缺少可选内容时提供自然降级，不展示空白占位。
- 用户可见页面、GitHub README、截图和公开文案只服务最终读者。
- 公开内容不得出现作者备注、开发流程、设计评审、录制安排、技术实现说明或内部验收文案，除非这些内容本身就是文章主题。

## 测试与验证

- 行为变化必须补充或更新相应测试。
- 修复 BUG 时先建立稳定复现，再验证修复和相关回归。
- 完成前运行当前项目定义的类型检查、Lint、测试和生产构建。
- 未运行的检查必须说明原因和风险。
- 页面任务至少检查核心路径、无效地址、手机尺寸、刷新、站内跳转和键盘操作。
- 部署任务必须验证公开地址、自动部署、关键资源和地区访问结果。

项目尚未建立可执行命令。在 Phase 1 核验并写入 DEV 前，不得虚构安装、测试或构建命令。

## Documentation Closeout Gate

每次任务或 Phase 结束前，严格执行 `../README.md` 中的 Documentation Closeout Gate：

- 更新当前 REQ 的状态、验收结果和证据。
- 在当日 PROG 追加完成内容、问题、阻塞和下一步。
- 按需要同步 PRD、BIZ、DEV 或 BUG。
- 更新文档索引。
- 检查引用、状态、矛盾、历史保留和模糊占位。

文档收尾不是可选附加项。未完成收尾时，不得宣称任务完成。

## Git 与外部操作

- 未经用户明确授权，不推送远程、不发布版本、不部署生产环境。
- 提交保持单一目的，只包含当前任务相关修改。
- 不提交密钥、`.env*`、日志、缓存、依赖目录和构建产物。
- 任何会改变外部状态的操作都必须符合用户当前授权范围。

## 完成交付

每次完成后必须说明：

- 改了什么
- 为什么这样改
- 如何验证
- 哪些检查未执行及原因
- 仍存在的风险
- 下一项最合理任务

无法完成的部分要明确说明，不承诺在对话之外自动完成。
